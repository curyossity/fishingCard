# Deepwater — Architecture

Current responsibility map: Discover → Land → Build / Upgrade, updated 19 November 2026 for five-tag content and effect implementation. The [GDD](Fishing_Card_Roguelike_GDD_with_image/Fishing_Card_Roguelike_GDD.md) governs mechanics; [Architecture Implementation Reference](Architecture%20Implementation%20Reference.md) preserves historical implementation details. Five-tag preparation, one-tag content and removal of secondary-tag preference are implemented; see [current validation](Validation/FiveTagAbilities/README.md).

## Ownership

| Owner | Responsibility |
| --- | --- |
| FishingRunController | Expedition phase, accepted creature occurrence, landing commands/outcomes, placement commitment, automatic duplicate resolution, continuation and exactly-once settlement |
| EncounterRuntime / slot runtime | Four prepared symbols chosen from five tags, three reels, one optional respin, explicit acceptance, eligible biome creature selection and occurrence identity |
| SlotCreatureSelector / SlotSelectionSettings | Separate rarity roll, tag guarantees, lower-tier nearest-rarity ties and unlock/Apex eligibility; no preference from a pair's unmatched symbol |
| LandingChallengeRuntime / LandingSettings | Absolute-clock motion, accuracy, points, attempts, protected Misses, feedback freeze and immediate success/failure |
| LandingScoring / LandingRigMember / LandingRigRule | Frozen committed-species/tag/level scoring, flat bonuses before multiplier products, explicit Miss rules and source attribution |
| RigRuntime | One ordered position per species, levels/copies, legal insertion, pure transactional previews, upgrades, removal, triggers, derived sale values and haul snapshots |
| CardDefinition / CreatureAbilityDefinition | Species content authority: identity, sprites, exactly one creature tag, base price, one primary-ability blueprint, descriptions, tuning and level progression; no expedition mutations |
| CardInstance | Stable runtime member identity, effective tags, temporary level/copies, frozen ability, completed value grants and current sale value |
| Progression / results | Permanent unlock/reward ownership under approved predicates; resolved full-haul snapshot before temporary rig cleanup |
| Views | Render authoritative state and forward occurrence/revision-bound commands; never decide score, legal placement or rewards |
| Editor authoring | Validate one supported tag and one primary ability per creature, effect-handler support, definitions and tuning; import approved sprites, create reusable phase prefabs and preserve scene/Harbor bindings |

## Phase and transaction boundaries

Every expedition begins in Shallows with an empty rig. Discover prepares four of five tags as active symbols and retains one optional lock/respin, keeping the final result visible until Accept Tags. A pair guarantees its repeated tag without a preference from the unmatched symbol. Creature selection creates the Landing occurrence without acquisition.

The GDD owns tag philosophies and shared mechanics. Editable creature definitions own species tags and primary abilities; Markdown does not duplicate the roster or per-species effect catalog. `RigAbilityText` resolves authored description tokens against current-level amounts for both card text and Build. Landing owns encounter-local sequences, per-rule trigger usage, encounter tag/rarity, assistance and strike resolution; the rig owner retains acquisition/upgrade grants and continuous positional/value recalculation. Fixed-grid fish-time integration preserves deterministic conditional slowing without changing the zone clock. Attempt grants retain source attribution in strike feedback. See [Creature Ability Authoring](Creature%20Ability%20Design.md) for supported handlers, shared contracts and assistance stacking.

Land captures only committed members, primary ability levels and effective tags. New acquisitions cannot assist their own challenge. Success reserves the landed species for Build; failure snapshots and pays the full accumulated haul once, excludes the failed creature, then clears every temporary member, level and copy. Permanent progression remains preserved. `FishingRunResult.RewardClaimed` prevents repeated payout.

A new species receives a side-effect-free placement preview and one explicit legal-gap commitment. A duplicate automatically upgrades its existing position with no placement prompt. Every landed copy contributes its base sale value. Continuous value effects derive from accumulated species value; acquisition and upgrade triggers are distinct. Existing relative order is preserved. No manual reorder, Catch/Bait, capacity or overload action participates in the redesigned run.

Rig mutations validate on independent candidate snapshots before replacing live state. Stale Build occurrences/rig revisions, invalid authoring, blocked gaps and arithmetic overflow cannot partially acquire a creature. Controller notifications follow authoritative commitment. Previews publish no acquisition effects. Removal is a gameplay-owner operation for explicitly defined effects, not a manual UI action; current removal preserves collected base value/completed grants and recalculates continuous effects.

`RigBuildingView` owns selection, native navigation, previews and the brief automatic upgrade display; `RigBuildingSetup` authors its separate Tackle canvas and binds it to `FishingRunView`. Its reusable cabinet/rail card prefabs retain independent faces, portraits and live labels. `TackleRigCardView` displays level and accumulated sale value. `RigAcquisitionReceipt` captures the upgraded member, prior level/haul and committed rig independently of the next encounter. The controller commits and continues once, blocks commands during receipt feedback, and accepts only the matching feedback occurrence for dismissal. The view dismisses automatically on an unscaled presentation timer, with no placement or confirmation action for duplicates. Discover remains hidden throughout that feedback. `LandingChallengeView` hides after successful landing. `SlotMachineSetup` retains all three phase bindings during regeneration.

The Build artwork follows the approved Penpot information layout. The 17 November 2026 correction replaces the generic shell and overlaid tray with one complete authored housing containing its wooden recess. `RigBuildingSetup` imports that source byte-for-byte into `Art/RigBuilding`, preserves the housing GUID and draws it proportionally at 1310 × 681 within the 1920 × 1080 stage. There are no separate tray-background fields, images or runtime sprites. All rig sizes use independent pooled faces, ropes, clips and insertion controls inside a 1020-wide horizontal viewport; longer rigs scroll. The exporter permits independent AssetLibrary image layers and an explicit whole-file copy of the integrated housing. `RigAbilityText` formats current-level authored effects; `TackleBuildTypography` aligns native glyph ink. The controller/model still own legal placement, acquisition and projected sale values. See [housing provenance](UIThemes/TackleApparatusConcept/BuildUpgradeRevision/IntegratedMachine/README.md) and [Build artwork validation](Validation/TackleBuildArt/README.md).

Landing uses a complete integrated interior variant of the Build master. `TackleMachineGeometry.StageBounds` is the shared outer position/size contract for all three phases. `NormalizeLandingHousing.cs` registers generated art only inside the two working recesses, inheriting every Build alpha value and all protected visible outer pixels. The imported Landing sprite contains its portrait plate, score readout, timing glass and readout wells; native content supplies values, the portrait, fill, fish, zones and variable attempt lamps. `TackleLandingArtSetup` rejects normalization hash mismatches before importing. `TackleLandingArtChecks` verifies every alpha value, protected exterior pixel, identical anchors/scale, native scoring widths and removal of old overlay backgrounds. This prepares a fixed shell for future transitions without adding a transition or changing rules. See [Landing source](UIThemes/TackleApparatusConcept/LandingIntegrated/README.md) and [validation](Validation/LandingIntegrated/README.md).

Discover's 18 November variants retain the same outside shell with a recessed wheel bay and integrated lock-control deck. `TackleDiscoverHousingSetup` imports the normalized whole housing, retaining the wheels' native projection coordinates. The current original-size variant uses the original 320 × 365 wheel dimensions and 100% scale, registered to the new housing’s measured socket centers; its enlarged interior removes the crossmember. The compact variant retains 72% wheel scale. Selection lives in a project JSON asset and survives full Discover regeneration. Menus switch between original-size/compact unified versions or restore the original machine. Both previous functional prefabs and sprite sources remain preserved. `TackleDiscoverHousingChecks` independently compares all three runtime PNG silhouettes, protected exterior pixels and stage transforms, plus the retained original composition and original-size wheel transforms. See [current source and version menus](UIThemes/TackleApparatusConcept/DiscoverIntegrated/FullSize/README.md) and [validation](Validation/DiscoverIntegrated/FullSize/README.md).

The framed Build v2 embeds Landing's creature frame and effects-panel border at their exact native positions, retaining the wooden rig and casing. The effects well has no progress trough. `RigBuildingSetup` removes `build-portrait`/`build-effect` overlay assets after replacing their prefab references; portrait and level/value/effect text remain native. `RigBuildingView` derives ability-scroll dimensions from its viewport. Pixel checks compare the frame geometry with Landing and verify unchanged artwork outside the upper working area. The insertion heading sits below both borders. See [frame provenance](UIThemes/TackleApparatusConcept/BuildUpgradeRevision/IntegratedMachine/FramesV2/README.md).

Biome completion predicates, final success endpoints, permanent grant tables, no-legal-position resolution and finalized species abilities remain design inputs. Authored special Apex encounters retain eligibility and are routed through Landing; Build does not invent an automatic completion reward or a new gate.

## Presentation and validation

Landing scoring freezes each contribution's current-level explanation and positional enabler identities alongside its exact bonus/multiplier/attempt grant. `FishingRunController.LastLandingStrike` captures committed pre-acquisition members, accumulated points and Resistance before terminal handling, survives continuation and failure cleanup, and clears at the next expedition start. `LandingStrikeFeedback` owns persistent source portraits, ordered addition/multiplier rows and ongoing assistance. `LandingContributionView` supplies pointer/native-focus explanations through the shared tooltip; `LandingActivationView` draws non-intercepting source/support outlines outside card faces and scroll masks. Build consumes the frozen winning receipt without replaying its celebration. `LandingStrikeFeedbackSetup` preserves these bindings in both phase-generation paths. See [strike-feedback validation](Validation/LandingStrikeFeedback/README.md).

`LandingScoreSequence` derives a bounded schedule from resolved operations; `LandingScoreRush` owns the growing readout, synchronized card kicks/outlines, offscreen-source portrait, musical steps and transfer into accumulated progress. `LandingRushGraphic` draws deterministic light trails and sparks without gameplay randomness. Authored PCM cues use six reusable 2D voices routed through the Landing feedback mixer. Sound and reduced-motion preferences affect presentation only. `LandingScoreRushSetup` retains these bindings during Landing regeneration.

The controller owns the skippable `LandingFeedbackPending` gate. Points and terminal outcomes resolve immediately; failure immediately pays the full haul and clears the rig, while frozen source members remain visible during feedback. `HoldPresentationClock` excludes the count-up from motion, and controller commands reject a second strike or early placement. After feedback or Space/Finish, a reserved duplicate upgrades automatically once, or a new species opens Build. Without an enabled score presentation there is no wait. The controller's bounded deadline prevents interrupted visuals from retaining the gate. See [score-rush validation](Validation/LandingScoreRush/README.md).

The 19 November [creature-art supplement](UIThemes/TackleApparatusConcept/CreatureSprites/Supplement20261119/README.md) extends the registered library to 25 illustrations, covering every standard creature. `CreatureSpriteSetup` records optional per-source low-alpha cleanup alongside crop provenance; legacy sources retain zero cleanup and unchanged imported hashes. `CreatureSpriteChecks.ValidateTo` writes isolated review evidence and sizes its native-card sheet to the registered roster without clipping later rows. See [supplement validation](Validation/CreatureSprites/Supplement20261119/README.md).

`TackleCardTooltip` owns one native, non-intercepting details overlay per Tackle phase, outside the cabinet/tray masks. `TackleCardTooltipSource` connects pooled faces to delayed pointer inspection and immediate native focus; recycling, scrolling and phase exit invalidate inspection. Bound member snapshots supply tag, level, resolved sale value and frozen primary-ability text through `RigAbilityText`. Build rail cards consume selected `RigRuntime.TryPreview` snapshots and explicitly label projected details; the cabinet retains committed members. Inspection issues no acquisition, scoring or placement commands. `TackleCardTooltipSetup` authors the reusable overlay and wires phase/card regeneration paths. See [tooltip validation](Validation/CardTooltips/README.md).

Follow [Card Visual Specification](Card%20Visual%20Specification.md). Keep sprites and reusable faces separate from native information, commands and feedback. `RigBuildingChecks` validates pure rig/scoring/value invariants using disposable definitions. `RigBuildingSceneChecks` exercises real strikes, independent phase visibility, native placement, duplicate upgrades, stale input, scrolling, complete failure payout and a clean next expedition with persistence disabled. See [Build validation](Validation/RigBuilding/README.md).

The installed Tackle Apparatus presentation uses `TackleDiscoverPresentation` for model-driven reel artwork, shared shell, haul and ordered rig; `TackleRigCardView` supplies separate face/portrait/level/value fields, and `TackleButtonFeedback` owns visual input feedback. `TackleDiscoverArtSetup` is the repeatable import/prefab/scene binding path. The separate 1920 × 1080 canvas appears only during Discover and hides at the landing handoff. Comparison-scene and Harbor regeneration retain the binding. It changes presentation only; see [Unity validation](Validation/TackleDiscoverArt/README.md) for captures, covered controls and missing illustration mappings.

Discover animation is presentation-only: `TackleReelAnimator` advances each cylinder toward the already resolved tag, while `TackleReelFace` and `CylindricalReelGraphic` project native TMP glyphs and subdivided sprite geometry onto the same surface. `TagSlotMachineRuntime.SpinRevision` identifies actual rolls independently of lock/accept revisions. `SlotMachineView.IsAnimating`, forwarded by `FishingRunView`, lets the controller reject lock/respin/accept commands during motion. The initial spin animates all reels; a respin leaves its locked reel stationary. Completion restores input and reveals match feedback without accepting a result or consuming gameplay randomness. Hiding the phase cancels visual work and callbacks.

`TackleReelSurface` owns private paper and optional outer-drum materials per wheel. Its shader inverse-projects the flat paper and the preserved drum's divider/plaque regions with exactly the native faces' rotation. Baseline wheels retain fixed rim samples; full-size wheels opt into rotating edge-material details while keeping the outline and directional shading fixed. Neighboring faces remain on the continuous cylinder and disappear into its edge shadow. `TackleReelSurfaceSetup` authors those layers, preserves the original image, and retains the installation through full Discover/animation regeneration. Runtime material instances are reused across visibility cycles and released with their view; shared authored materials are never animated.

Full-size Discover reels use a `ReelApertureMask` stencil traced from the preserved drum's inner edge. `TackleReelApertureSetup` places the moving paper plus `TackleReelAnimator`'s native-face content under the same curved aperture. A separately bound outer drum layer rotates its sampled wear/bevel seams with the same phase, while preserving the source alpha, thin socket lip and fixed lighting. `TackleReelSurface` owns both private materials and updates uGUI's cached stencil-derived rendering copy. The wider center and narrower ends clip consistently without changing cylinder geometry, placement or timing. Compact restoration removes the wrapper and clears optional face/edge bindings; archived prefabs remain untouched. `ReelApertureChecks` verifies actual GPU clipping, shared face ownership and rendered phase. `ReelEdgeMotionChecks` compares band pixels at two angles while independently checking that the outer lip remains still; live animation checks cover locked edge phases. See [edge-motion validation](Validation/DiscoverIntegrated/FullSize/RotatingEdges/README.md) and [curved-aperture validation](Validation/DiscoverIntegrated/FullSize/CurvedAperture/README.md).

`TackleReelSymbolSetup` binds the five gameplay tags using supplied reel illustrations; retired image resources remain preserved. Full Discover regeneration uses that mapping. `FiveTagPresentationSetup` migrates saved native Harbor buttons and Discover mappings without rebuilding approved artwork. Supplemental originals, generation prompts and hashes remain separate from the original Penpot export manifest.

`TackleReelAnimationSetup` persists the presentation choice between continuous material wear and segmented brass bands. The shared shader retains both branches; `TackleReelSurface` serializes the selected enum and forwards it to both private/stencil-derived layers. Material and housing authoring reapply the project JSON selection. The segmented alternative uses angle-projected joints/rivets with the existing motion, geometry, clipping and locked-reel rules. The earlier style and preview remain available through the Reel Motion menu. See [motion alternatives](Validation/DiscoverIntegrated/FullSize/SegmentedBands/README.md).

`CreatureSpriteSetup` imports the selected Penpot creature library, verifies roster identities/source hashes, removes transparent margins without resampling and assigns the resulting sprites to `CardDefinition.Artwork` and `EncounterArtwork`. Those definition fields are authoritative for creature/Apex illustrations in Tackle rig cards, Landing portraits, generic card views and the Journal central/compact views. Separate four-species Tackle portrait lists are removed. Journal frames, geometry and non-creature art retain their theme ownership. Discover/Landing authoring calls the same importer, so regeneration cannot restore obsolete creature illustrations. `CreatureSpriteChecks` exercises all 22 definitions through the actual view prefabs; provenance and captures are under [creature artwork validation](Validation/CreatureSprites/README.md). The moving Landing indicator remains independent, generic artwork.
