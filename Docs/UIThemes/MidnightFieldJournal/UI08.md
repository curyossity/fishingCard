## Standalone build blocker

Two explicit local development builds targeted Windows x64 with comparison scene first and original scene second. Both stalled at `BuildPlayerDataGenerator` behind a Windows `cmd.exe /c` worker that never launched its generator child. The actual player assemblies were produced, but packaging never completed. Only the confirmed build-owned waiting shells were stopped to recover the Editor. A direct generator invocation produced its expected JSON files, but the next Unity build reproduced the shell stall. No system shell/registry, package, rendering, PlayerSettings or default scene-list change was made to bypass it.

[Attempt one](UI08BuildAttempt1.json) and [attempt two](UI08BuildAttempt2.json) record failed builds with unchanged EditorBuildSettings. Their generic post-termination build errors are not passing compilation or player-smoke evidence. No executable was produced; the standalone player smoke and player performance measurements **were not run**. The opt-in development-player runner remains available via `-journal-smoke-output <absolute-directory>` once the local build-worker issue is resolved. `JournalReleaseChecks.BuildPlayer()` reproduces the explicit local build without changing the default build list.

Unity's build-time saves also serialized previously dirty font caches, rendering/settings migrations and Input System preload data. All nine affected existing files were restored only after reconstructed bytes matched their pre-task SHA256; pre-existing user line endings were retained. See [restoration evidence](UI08BuildAutosaveRestoration.json). Newly generated Performance Test Resources were moved to ignored `Temp/MidnightFieldJournal/BuildAutosaves/GeneratedResources`, so they do not become new runtime content. No further build/global asset save was run after restoration.
