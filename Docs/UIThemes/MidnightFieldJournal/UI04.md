# UI-04 — engraved Technique hand and perspective

Implemented a reusable controller-facing hand with individual data-bound cards and genuine perspective. It uses the latest engraved V2 sources and the later laid-down hand as the visual reference. The flattened reference image is not a runtime asset. SampleScene, the original design and the build selection remain unchanged; full gameplay-scene installation remains UI-07.

## Delivered behavior

- `Prefabs/TechniqueHand.prefab` contains the shared `TechniqueHandView` endpoint and a `JournalTechniqueHandPresentation`. The optional shared `TechniqueHandPresentation` seam leaves the old renderer as the default for existing scenes/prefabs.
- Each actual hand slot has its own `TechniqueCardView`, approved frame, optional exact-ID illustration, live title/type/rules, input button and independent state layers. The eight active designs remain active. Duplicate definitions get separate physical views and callbacks using current hand indices.
- A private perspective camera renders the card planes to a transparent RenderTexture on the hand's HUD surface. Text, art, frame and shadows share each plane. Camera Field of View is 35°, rest tilt is 40°, reference distance is 1500 UI-world units, and four-card spacing is 550. These are Unity-authored settings tuned against the reference, not measurements inferred from Penpot. Narrower viewports move the camera back to keep the cards in frame.
- Hover or navigation focus straightens a card to 10° and lifts it to an inspect pose. A stable resting hit plane prevents hover loss when the visible card moves. Hits respect actual sibling order when hover and navigation focus overlap. Exiting/clearing focus or hiding the hand restores the resting pose.
- `JournalHandRaycaster` maps HUD points to the perspective camera and returns the actual card target through Unity's EventSystem. Results participate in the owning canvas's normal depth/modal sorting. The camera's own raycaster is called only with mapped coordinates and is excluded from global raycaster registration.
- `JournalTechniqueButton` rejects a click when the hand changes between pointer press and release. `FishingRunController` passes the existing deck `HandVersion` to the view; this adds no gameplay state or new action. Normal refreshes reuse listeners/views and do not duplicate callbacks.
- Navigation uses the real card buttons in hand order. Unavailable cards can still be inspected, including their controller-provided reason outside the printed face; pointer/submit use remains blocked. The offscreen views also respect HUD CanvasGroup input locks.
- The approved four examples have presentation-only word breaks in the theme profile. Every live rule word is preserved, including when source descriptions change. Shared card definitions are not edited. The old cards retain their original fitting, availability and hover defaults.
- Render targets follow the hand's output-pixel dimensions, including 2500 × 866 at the reference layout and 1250 × 433 at half scale. Width is capped at 3840 and height at 2160. Rendering occurs on content/pose/output-size changes. Disabling or destroying the hand releases its target and detached stage; re-enabling restores current content and counts.

The detached world-space UI stage uses layer 31 and sits at Z 100000, outside the gameplay camera's normal frustum. Its private camera renders only that layer and its local depth range. It creates no lights, physics, game-world entities or gameplay mechanics. All stage resources are owned by the hand and excluded from scene saving. The HUD surface retains the modal/tooltip composition order. Player GPU/memory cost and full-screen composition remain UI-08 checks.
